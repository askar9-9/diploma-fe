# ADR Функциональная спецификация сервисов HomeIQ

**Статус:** Принято  
**Дата:** 2026-05-19  
**Автор:** Дипломная работа — «Разработка системы управления умным домом на основе методов машинного обучения»  
**Методология:** Spec-Driven Development (SDD)

---

## Назначение документа

Данный ADR описывает функциональную спецификацию каждого сервиса системы HomeIQ как самостоятельного приложения. Документ определяет **что** делает каждый сервис, **зачем** он существует и **какие** возможности предоставляет — без описания интерфейсных контрактов и кода реализации.

Спецификации из этого документа являются основой для написания детальных spec-файлов (`specs/<layer>/<task>.md`), которые, в свою очередь, порождают тесты и реализацию по циклу SDD: Spec → Red → Green → Refactor.

---

## Общая архитектура

Система HomeIQ состоит из пяти сервисов, развёрнутых в Docker Compose:

```
┌───────────────────────────────────────────────────────────────────┐
│                          Docker Compose                           │
│                                                                   │
│  ┌──────────────┐           ┌───────────────────────────────┐    │
│  │   Frontend   │◄─────────►│         Backend API           │    │
│  │  React + TS  │  REST/WS  │       FastAPI  :8000          │    │
│  │  Nginx  :80  │           └──────┬───────────┬────────────┘    │
│  └──────────────┘                  │            │                 │
│                            ┌───────▼──────┐  ┌─▼─────────────┐  │
│                            │  ML Service  │  │   Mosquitto   │  │
│                            │  FastAPI     │  │  Broker :1883 │  │
│                            │  :8001       │  └─▲─────────────┘  │
│                            └──────────────┘    │                 │
│                                            ┌───▼─────────────┐  │
│                                            │Device Simulator │  │
│                                            │  Python  :8002  │  │
│                                            └─────────────────┘  │
│                                                                   │
│  ┌──────────────────────────────────────────────────────────┐    │
│  │                        SQLite                            │    │
│  └──────────────────────────────────────────────────────────┘    │
└───────────────────────────────────────────────────────────────────┘
```

**Принцип разделения:** каждый сервис отвечает за одну зону ответственности. Frontend — отображение и взаимодействие с пользователем. Backend — оркестрация, хранение данных, маршрутизация команд. ML Service — чистый инференс и обучение моделей. Device Simulator — имитация физических IoT-устройств. Mosquitto — транспорт сообщений между IoT-уровнем и бэкендом.

## 1. Frontend

**Контейнер:** `frontend`  
**Порт:** 80  
**Стек:** React 18, TypeScript, Vite, Tailwind CSS, раздаётся через Nginx  
**Роль:** единственная точка взаимодействия пользователя с системой

### 1.1 Общее описание

Frontend — это одностраничное веб-приложение (SPA), через которое пользователь наблюдает за состоянием умного дома, управляет устройствами, просматривает решения ML-модели и запускает демонстрационные симуляции. Приложение не содержит бизнес-логики — вся логика сосредоточена в Backend и ML Service. Frontend только отображает данные и транслирует пользовательские действия в запросы к Backend.

### 1.2 Навигация и структура страниц

Приложение состоит из шести основных разделов, доступных через боковую навигационную панель (sidebar). Sidebar всегда видим, содержит иконки и названия разделов, а также индикатор текущего активного сценария в нижней части.

#### 1.2.1 Dashboard (Главная панель)

**Назначение:** обзорная страница, дающая полную картину состояния дома за один взгляд.

**Функциональность:**

Верхняя часть страницы отображает текущий активный сценарий (например, «Ночь») с цветовой индикацией и иконкой. Рядом — уровень уверенности ML-модели в текущем решении, представленный как процентная шкала с цветовой градацией: зелёный при высокой уверенности (от 80%), жёлтый при средней (60–80%), красный при низкой (ниже 60%).

Центральная часть — сетка карточек устройств. Каждая карточка показывает имя устройства, его текущее состояние (включено/выключено, числовое значение) и иконку типа устройства. Бинарные устройства (датчики движения, выключатели) отображаются с цветовым индикатором: зелёный — активен, серый — неактивен. Аналоговые устройства (температура, освещённость) показывают текущее значение и мини-график последних значений за час.

Нижняя часть — лента последних событий (event log). Отображаются последние 20 событий в хронологическом порядке: смена состояния устройства, активация сценария, предложение нового паттерна. Каждое событие содержит временную метку, источник (устройство или ML) и краткое описание.

Все данные на Dashboard обновляются в реальном времени через WebSocket-подключение. При потере соединения отображается уведомление с предложением переподключиться.

#### 1.2.2 Devices (Устройства)

**Назначение:** детальное управление каждым виртуальным устройством умного дома.

**Функциональность:**

Страница представляет список всех зарегистрированных устройств в виде расширяемых карточек. Устройства сгруппированы по типу: сенсоры (датчики движения, температуры, освещённости), актуаторы (свет, термостат), медиа (телевизор).

Каждая карточка устройства содержит: название, тип, текущее состояние и элемент управления. Для бинарных устройств — переключатель (toggle). Для числовых (температура, освещённость) — слайдер с отображением текущего и целевого значений. При изменении состояния пользователем фронтенд отправляет команду в Backend, который транслирует её в Device Simulator через MQTT.

В расширенном виде карточка показывает историю изменений состояния устройства за последние 24 часа в виде графика-таймлайна. Это позволяет на защите диплома продемонстрировать, как менялись показания устройства в ходе симуляции.

#### 1.2.3 Scenarios (Сценарии)

**Назначение:** просмотр и управление сценариями умного дома.

**Функциональность:**

Страница отображает все существующие сценарии в виде карточек. Каждый сценарий содержит: название, описание, набор устройств и их целевых состояний при активации, и признак — стандартный (предустановленный) или пользовательский (созданный через Pattern Suggester).

Предустановленные сценарии: «День» (day), «Ночь» (night), «Никого нет» (away), «Кино» (movie). Для каждого отображается, какие устройства в какое состояние переводятся при активации.

Пользователь может активировать любой сценарий вручную кнопкой «Активировать». При активации фронтенд отправляет запрос в Backend, тот публикует команду в MQTT, Device Simulator исполняет сцену, и результат возвращается через WebSocket на Dashboard.

Также доступна функция создания нового сценария. Пользователь задаёт имя, выбирает устройства и их целевые состояния из выпадающих списков. Новый сценарий сохраняется в базу данных через Backend и становится доступен для ML-классификатора после дообучения.

#### 1.2.4 ML Insights (ML-аналитика)

**Назначение:** визуализация работы ML-модели — ключевая страница для демонстрации на защите диплома.

**Функциональность:**

Раздел разделён на три вкладки.

**Вкладка «Классификатор»** показывает текущий прогноз модели: предсказанный сценарий, уверенность, альтернативный сценарий. Также отображается столбчатая диаграмма вероятностей всех классов (day, night, away, movie) — это позволяет наглядно увидеть, насколько уверенно модель разделяет сценарии. Под диаграммой — линейный график уверенности во времени (последние N решений), демонстрирующий стабильность классификатора.

**Вкладка «Кластеризация»** визуализирует пространство признаков после PCA-проекции в 2D. Каждая точка — один feature vector из истории. Цвет точки соответствует кластеру K-Means. Известные сценарии помечены отдельным маркером, неизвестные кластеры выделяются контрастным цветом. Это главная визуализация научной новизны — обнаружение новых паттернов без разметки. Рядом с графиком — легенда: какой кластер соответствует какому сценарию, и какие кластеры пока не классифицированы.

**Вкладка «История решений»** представляет таблицу последних N feature vectors с колонками: время, значения всех 8 признаков, предсказанный сценарий, уверенность, источник решения (classifier / clusterer / manual). Таблица поддерживает сортировку по любому столбцу и фильтрацию по сценарию. Данные можно экспортировать в CSV для включения в текст дипломной работы.

#### 1.2.5 Pattern Review (Обзор паттернов)

**Назначение:** интерфейс для пользовательского подтверждения или отклонения новых паттернов, обнаруженных K-Means кластеризатором.

**Функциональность:**

Когда ML-модель обнаруживает повторяющийся кластер, не соответствующий ни одному известному сценарию, Backend формирует предложение нового паттерна. Эта страница отображает список таких предложений.

Каждое предложение содержит: описание временного окна (например, «18:00–20:00»), дни недели, в которые паттерн наблюдался, характерные состояния устройств (какие сенсоры активны, уровень света и температуры), количество повторений и дату первого обнаружения.

Для каждого предложения доступны две кнопки: «Подтвердить» и «Отклонить». При подтверждении пользователь может задать имя нового сценария (например, «Вечерний отдых»). После подтверждения Backend отправляет данные в ML Service для дообучения классификатора — новый класс добавляется в модель. При отклонении паттерн помечается как отвергнутый и больше не предлагается.

Отдельно отображается архив: ранее подтверждённые и отклонённые паттерны с датами решений.

#### 1.2.6 Simulation (Симуляция)

**Назначение:** панель управления демонстрационной симуляцией для защиты диплома.

**Функциональность:**

Центральный элемент — кнопка «Запустить симуляцию дня». При нажатии Device Simulator начинает воспроизводить типичное поведение обитателя дома за 24 часа в ускоренном режиме.

Настройки перед запуском: коэффициент ускорения (по умолчанию ×30 — полные сутки за 48 секунд, можно выбрать ×10, ×60, ×120 для разных целей демонстрации).

Во время симуляции отображаются: прогресс-бар с текущим виртуальным временем (0:00 → 23:59), текущее состояние всех устройств (обновляется в реальном времени), и log принятых ML-решений. Пользователь видит, как ML-модель реагирует на меняющиеся условия: утром активирует «День», вечером при включённом ТВ — «Кино», ночью — «Ночь», при отсутствии движения — «Никого нет».

Кнопка «Остановить» прерывает симуляцию. Кнопка «Сбросить» возвращает все устройства в начальное состояние.

Отдельная кнопка «Симулировать неделю» прокручивает 7 виртуальных суток подряд — это необходимо для демонстрации обнаружения новых паттернов кластеризатором, которому нужно скользящее окно в 7 дней.

### 1.3 Сквозные функциональные требования

**Реальное время.** Все изменения состояний устройств и ML-решений отображаются мгновенно через WebSocket. Пользователю не нужно обновлять страницу.

**Адаптивность.** Интерфейс корректно отображается на экранах от 1024px (ноутбук для демо на защите) до 1920px (монитор). Мобильная адаптация не требуется — система рассчитана на десктопный демонстрационный режим.

**Состояние подключения.** В шапке приложения — индикатор статуса WebSocket-соединения. Зелёная точка — подключено. Красная — потеряно соединение, с автоматической попыткой переподключения каждые 5 секунд.

**Авторизация.** Простая JWT-авторизация: логин / пароль → получение токена → использование токена для всех запросов. Одна роль — администратор. Регистрация не предусмотрена — демонстрационная система с предустановленными credentials.

**Темы оформления.** Поддержка светлой и тёмной темы через переключатель в шапке. По умолчанию — тёмная тема (лучше смотрится на презентации).

## 2. Backend API

**Контейнер:** `backend`  
**Порт:** 8000  
**Стек:** Python 3.11, FastAPI, SQLAlchemy, paho-mqtt  
**Роль:** центральный оркестратор системы — единственная точка входа для фронтенда, посредник между ML-сервисом и IoT-уровнем

### 2.1 Общее описание

Backend — это серверное приложение, выполняющее четыре ключевые функции: обслуживание REST-запросов от фронтенда, трансляция команд между фронтендом и IoT-устройствами через MQTT, координация ML-инференса (отправка feature vectors в ML Service и обработка ответов) и хранение данных в SQLite.

Backend не содержит ML-логики — он только передаёт данные в ML Service и обрабатывает результат. Backend не управляет устройствами напрямую — он отправляет команды в MQTT, а Device Simulator их исполняет.

### 2.2 Функциональные области

#### 2.2.1 Управление устройствами

Backend хранит реестр всех виртуальных устройств и их текущие состояния в базе данных. При получении MQTT-сообщения от Device Simulator об изменении состояния устройства Backend обновляет запись в БД, сохраняет событие в таблицу событий и оповещает всех подключённых WebSocket-клиентов.

При получении запроса от фронтенда на изменение состояния устройства Backend публикует соответствующую команду в MQTT-топик, адресованный Device Simulator.

#### 2.2.2 Управление сценариями

Backend хранит определения сценариев (какие устройства в какие состояния переводить) и предоставляет операции: получение списка сценариев, создание нового сценария, активация сценария (публикация команды в MQTT), удаление пользовательского сценария.

При получении подтверждения от Device Simulator о выполнении сцены Backend обновляет текущий активный сценарий и оповещает WebSocket-клиентов.

#### 2.2.3 Координация ML-инференса

Это центральная функция Backend. При каждом изменении состояния устройства Backend выполняет следующий цикл:

1. Собирает текущий snapshot всех устройств.
2. Строит feature vector из 8 признаков по каноническому Feature Schema.
3. Отправляет вектор в ML Service для классификации.
4. Получает ответ: предсказанный сценарий и уверенность.
5. Если уверенность выше порога — публикует команду активации сценария в MQTT.
6. Если уверенность ниже порога — запрашивает у ML Service кластерный анализ.
7. Сохраняет feature vector и результат в БД.
8. Оповещает WebSocket-клиентов о принятом решении.

Для построения feature vector Backend использует виртуальное время из Device Simulator (если активна симуляция) или системное время.

#### 2.2.4 Управление паттернами

Backend принимает от ML Service уведомления о новых обнаруженных паттернах, сохраняет их в базу данных со статусом «ожидает» и оповещает WebSocket-клиентов для отображения на странице Pattern Review.

При подтверждении паттерна пользователем Backend отправляет команду на дообучение в ML Service с новыми размеченными данными. При отклонении — обновляет статус в БД.

#### 2.2.5 Управление симуляцией

Backend проксирует команды управления симуляцией (запуск, остановка, сброс) от фронтенда к Device Simulator и транслирует статус симуляции обратно. Это позволяет фронтенду не знать о существовании Device Simulator — он общается только с Backend.

#### 2.2.6 WebSocket-вещание

Backend поддерживает постоянные WebSocket-соединения с фронтендом. Через них транслируются четыре типа событий: изменение состояния устройства, активация сценария, новое ML-решение (с уверенностью и источником), предложение нового паттерна.

WebSocket-менеджер отслеживает подключённых клиентов и обеспечивает broadcast всем при каждом событии.

#### 2.2.7 Хранение данных

Backend управляет SQLite-базой данных с пятью основными сущностями: устройства (реестр и текущие состояния), события (сырой лог всех изменений состояний), feature vectors (построенные векторы признаков с результатами ML), сценарии (определения и команды), предложенные паттерны (обнаруженные кластеризатором паттерны с их статусами).

#### 2.2.8 Авторизация

Backend реализует JWT-авторизацию. Один предустановленный пользователь с фиксированными credentials для демонстрации. При успешном входе — выдача JWT-токена. Все остальные endpoints защищены — требуют валидный токен в заголовке.

### 2.3 MQTT-подписки и публикации

Backend является MQTT-клиентом и выполняет две роли: подписчик (слушает сообщения от Device Simulator о состояниях устройств и подтверждениях сцен) и издатель (публикует команды активации сцен и изменения состояний устройств).

## 3. ML Service

**Контейнер:** `ml-service`  
**Порт:** 8001  
**Стек:** Python 3.11, FastAPI, scikit-learn, pandas, joblib  
**Роль:** чистый ML-движок — принимает данные, возвращает решения, обучает модели

### 3.1 Общее описание

ML Service — изолированный сервис, реализующий всю ML-логику системы. Он не подключён к MQTT, не имеет доступа к базе данных Backend и не знает о существовании устройств. Сервис оперирует исключительно числовыми feature vectors и возвращает решения в виде структурированных ответов.

Такая изоляция — архитектурное решение, обеспечивающее чистоту тестирования (ML тестируется без инфраструктурных зависимостей) и возможность замены модели без изменения остальной системы.

### 3.2 Функциональные области

#### 3.2.1 Классификация сценариев (Random Forest)

Основная функция — по входному feature vector из 8 признаков определить наиболее вероятный сценарий из набора известных классов.

Модель возвращает: имя предсказанного сценария, уверенность (вероятность наиболее вероятного класса), вероятности всех классов (для визуализации на фронтенде) и альтернативный сценарий (второй по вероятности).

Предобученная модель загружается из файла при старте сервиса. Начальные классы: day, night, away, movie. Набор классов расширяется при дообучении.

#### 3.2.2 Кластерный анализ (K-Means)

Вторая функция — обнаружение паттернов в массиве feature vectors без разметки. Backend отправляет массив исторических векторов (скользящее окно 7 дней), ML Service выполняет кластеризацию и возвращает: количество обнаруженных кластеров, принадлежность каждого вектора к кластеру, центроиды кластеров, и расстояния от текущего вектора до каждого центроида.

Модель K-Means переобучается при каждом запросе на новом массиве данных — это обеспечивает адаптивность к меняющемуся поведению.

#### 3.2.3 Обнаружение паттернов (Pattern Suggester)

Pattern Suggester — логический компонент, работающий поверх результатов кластеризации. Он анализирует кластеры и определяет, есть ли среди них повторяющиеся неизвестные паттерны.

Логика: если кластер не соответствует ни одному известному сценарию (определяется по расстоянию центроида от центроидов известных классов) и встречается N или более раз за сутки — формируется предложение. Предложение содержит: характерное временное окно, типичные дни недели, медианные значения признаков в кластере и количество наблюдений.

Это ключевой компонент научной новизны дипломной работы — автоматическое обнаружение новых сценариев без ручной разметки.

#### 3.2.4 Дообучение классификатора

При подтверждении нового паттерна пользователем Backend отправляет в ML Service набор feature vectors с новой меткой класса. ML Service дообучает Random Forest на расширенном наборе данных (старые данные + новые размеченные) и сохраняет обновлённую модель.

Сервис поддерживает версионирование моделей: каждая версия сохраняется с временной меткой, что позволяет откатиться к предыдущей версии при необходимости.

#### 3.2.5 Информация о модели

ML Service предоставляет метаинформацию: текущая версия модели, дата последнего обучения, количество классов, accuracy на тренировочных данных и количество обработанных запросов с момента запуска. Эта информация отображается на странице ML Insights фронтенда.

### 3.3 Данные и модели

Синтетический тренировочный датасет хранится в файле `data/synthetic_train.csv` внутри контейнера. Обученные модели сохраняются в `data/models/` с помощью joblib. Feature Schema (8 признаков) — каноническая и единая для всей системы, определена в CLAUDE.md.

## 4. Device Simulator

**Контейнер:** `device-simulator`  
**Порт:** 8002  
**Стек:** Python 3.11, FastAPI, paho-mqtt  
**Роль:** виртуальный IoT-слой — имитирует физические устройства умного дома

### 4.1 Общее описание

Device Simulator заменяет реальные IoT-устройства и платформу Home Assistant. Он хранит в памяти состояния всех виртуальных устройств, публикует изменения в MQTT при любом обновлении и исполняет сцены по команде из Backend.

Сервис существует потому, что: система не требует реального оборудования для демонстрации; написанный с нуля симулятор демонстрирует понимание IoT-протоколов (для академической ценности диплома); полный контроль над поведением устройств позволяет создавать детерминированные демонстрации.

### 4.2 Функциональные области

#### 4.2.1 Реестр виртуальных устройств

Device Simulator управляет набором виртуальных устройств, имитирующих реальные IoT-сенсоры и актуаторы умного дома.

**Сенсоры (датчики):**

Датчик движения в коридоре (`motion_hall`) — бинарный сенсор, фиксирующий наличие или отсутствие движения. В реальной системе — PIR-датчик. В симуляторе — переключается программно или при симуляции дня.

Датчик движения в гостиной (`motion_living`) — аналогичен датчику коридора, но для жилой зоны. Два датчика позволяют ML-модели различать активность в разных зонах дома.

Датчик температуры (`temperature`) — числовой сенсор в диапазоне 15.0–30.0°C. Имитирует комнатный термометр. Значение плавно меняется при работе термостата.

Датчик освещённости (`light_level`) — числовой сенсор в диапазоне 0–100. Значение зависит от времени суток (при симуляции) и состояния источников света.

**Актуаторы (исполнительные устройства):**

Потолочный свет (`ceiling_light`) — бинарный актуатор (включён / выключен). Управляется через сцены или вручную.

Ночник (`bedside_light`) — бинарный актуатор. Включается в ночном сценарии.

Термостат (`thermostat`) — числовой актуатор, задающий целевую температуру (17–25°C). При изменении уставки датчик температуры плавно подстраивается к целевому значению (имитация инерции).

Телевизор (`tv_on`) — бинарный актуатор. Ключевой признак для сценария «Кино».

#### 4.2.2 Исполнение сцен

Device Simulator получает из MQTT команды на активацию сцен. Каждая сцена — набор целевых состояний устройств. При получении команды симулятор: устанавливает все устройства в целевые состояния, публикует обновлённые состояния каждого устройства в MQTT и отправляет подтверждение выполнения сцены.

Четыре предустановленные сцены:

«День» — потолочный свет включён, освещённость 100, термостат на 22°C, ТВ выключен.

«Ночь» — потолочный свет выключен, ночник включён, освещённость 10, термостат на 20°C, ТВ выключен.

«Никого нет» — всё освещение выключено, освещённость 0, термостат снижен до 17°C (энергосбережение), ТВ выключен.

«Кино» — потолочный свет приглушен, освещённость 20, ТВ включён, термостат на 22°C.

#### 4.2.3 Симуляция дня

Ключевая функция для демонстрации. Симулятор воспроизводит типичный день жильца умного дома за ускоренное время.

Логика поведения по часам: ночью (0:00–6:00) — нет движения, всё выключено, свет минимальный. Утро (7:00–8:00) — движение в коридоре и гостиной, свет включается, температура поднимается. День (9:00–17:00) — периодическое движение, нормальная температура и освещённость. Вечер (18:00–22:00) — движение в гостиной, с вероятностью включается ТВ (сценарий «Кино»). Ночь (23:00–23:59) — движение прекращается, свет гаснет.

Каждый «час» симулятор обновляет виртуальное время, устанавливает состояния устройств согласно профилю поведения, добавляет элемент случайности (движение появляется с вероятностью, зависящей от времени суток) и публикует все изменения в MQTT. Между «часами» выдерживается пауза, зависящая от коэффициента ускорения.

#### 4.2.4 Управление виртуальным временем

Device Simulator хранит значение виртуального времени (`simulated_time`), которое используется вместо системных часов во время симуляции. Backend читает это значение при построении feature vector (поле `hour_of_day`).

Вне симуляции виртуальное время можно выставить вручную через запрос — это позволяет протестировать реакцию ML-модели на конкретный час без ожидания.

#### 4.2.5 Ручное управление

Помимо автоматической симуляции, каждое устройство можно переключить вручную через REST-запрос от Backend. Это используется фронтендом на странице Devices для ручного управления.

### 4.3 MQTT-взаимодействие

Device Simulator является MQTT-клиентом. Как издатель — публикует изменения состояний устройств и подтверждения выполнения сцен. Как подписчик — слушает команды активации сцен и изменения состояний от Backend.

## 5. Mosquitto (MQTT Broker)

**Контейнер:** `mosquitto`  
**Порт:** 1883  
**Образ:** eclipse-mosquitto:2  
**Роль:** шина сообщений между IoT-уровнем (Device Simulator) и Backend

### 5.1 Общее описание

Mosquitto — стандартный MQTT-брокер, выполняющий роль посредника для асинхронного обмена сообщениями. Это единственный компонент системы, который не разрабатывается с нуля — используется готовый образ. Выбор MQTT обоснован тем, что это отраслевой стандарт для IoT-систем (используется в Zigbee2MQTT, AWS IoT, Azure IoT Hub), и его присутствие в архитектуре академически значимо.

### 5.2 Функциональность

Брокер обеспечивает: маршрутизацию сообщений между издателями и подписчиками по топикам, гарантию доставки на уровне QoS 0 (at most once — достаточно для демонстрации), хранение retain-сообщений (последнее состояние каждого устройства доступно при подключении нового клиента).

### 5.3 Топиковое пространство

Топики организованы по трём направлениям потоков.

Поток «Устройство → Backend»: изменения состояний устройств и подтверждения выполнения сцен. Направление: Device Simulator публикует, Backend подписан.

Поток «Backend → Устройство»: команды активации сцен и ручного изменения состояний. Направление: Backend публикует, Device Simulator подписан.

Конкретные имена топиков определяются на этапе спецификации интерфейсных контрактов.

### 5.4 Конфигурация

Минимальная конфигурация: анонимный доступ (без аутентификации — демонстрационная среда), прослушивание на порту 1883, логирование в stdout для отладки. Конфигурационный файл монтируется из `mosquitto/config/mosquitto.conf`.

## 6. База данных (SQLite)

**Расположение:** файл `data/homeiq.db` в volume контейнера Backend  
**Стек:** SQLite через SQLAlchemy  
**Роль:** персистентное хранение всех данных системы

### 6.1 Общее описание

SQLite выбран как СУБД по нескольким причинам: отсутствие необходимости в отдельном контейнере (упрощает Docker Compose), достаточная производительность для демонстрационного объёма данных (тысячи записей, не миллионы), и нулевая конфигурация (файл создаётся автоматически при первом запуске).

### 6.2 Хранимые сущности

**Устройства.** Реестр виртуальных устройств: идентификатор, имя, тип, текущее состояние и атрибуты. Обновляется при каждом изменении состояния.

**События.** Хронологический лог всех изменений состояний устройств. Каждая запись: временная метка, идентификатор устройства, новое состояние, атрибуты. Используется для отображения ленты событий на Dashboard и для формирования скользящего окна данных для кластеризатора.

**Feature vectors.** Построенные векторы признаков с результатами ML-инференса: все 8 признаков, предсказанный сценарий, уверенность, источник решения (classifier / clusterer / manual). Используется для визуализации на странице ML Insights и экспорта в CSV.

**Сценарии.** Определения сцен: имя, отображаемое название, набор команд (целевые состояния устройств), признак пользовательского сценария, дата создания. Предустановленные четыре сценария создаются при инициализации БД.

**Предложенные паттерны.** Обнаруженные кластеризатором паттерны: идентификатор кластера, описание (временное окно, дни недели, характерные значения), количество повторений, статус (ожидает / подтверждён / отклонён), дата обнаружения.

## Рассмотренные архитектурные альтернативы

### Вариант A: Монолит (Backend + ML + Simulator в одном сервисе)

Объединение всей серверной логики в одно приложение упрощает деплой и межсервисное взаимодействие — нет HTTP-вызовов между сервисами, нет проблем с сетевой связностью. Однако это противоречит принципу разделения ответственности: ML-логику невозможно тестировать отдельно от MQTT-инфраструктуры, а замена модели требует пересборки всего бэкенда. Для дипломной работы демонстрация микросервисной архитектуры имеет самостоятельную академическую ценность.

### Вариант B: Текущая архитектура — 5 сервисов (выбран)

Каждый сервис отвечает за одну зону: Frontend — за отображение, Backend — за оркестрацию, ML Service — за инференс, Device Simulator — за IoT-имитацию, Mosquitto — за транспорт. Сервисы общаются по двум протоколам: HTTP REST (синхронные запросы Backend → ML Service, Frontend → Backend) и MQTT (асинхронные сообщения Backend ↔ Device Simulator). Это добавляет сложность деплоя (5 контейнеров вместо 2), но обеспечивает изолированное тестирование, независимое масштабирование и чёткую файловую структуру для параллельной разработки.

### Вариант C: Полностью событийная архитектура (все через MQTT)

Вариант, в котором ML Service и Frontend также общаются через MQTT без REST. Теоретически элегантен — единый транспорт для всей системы. Практически неудобен: фронтенд не может легко подписаться на MQTT из браузера без дополнительного WebSocket-моста, а синхронные запросы к ML Service (классифицируй вот этот вектор и верни результат) плохо ложатся на pub/sub-модель. MQTT оставлен только для IoT-уровня — там он стандартен и уместен.

### Почему MQTT оставлен для IoT-уровня

MQTT — отраслевой стандарт для IoT (Zigbee2MQTT, AWS IoT Core, Azure IoT Hub). Его наличие в архитектуре академически обосновано и демонстрирует знание IoT-протоколов. Для связи между Backend и Frontend использован WebSocket (стандарт для real-time веб-приложений), а для Backend и ML Service — HTTP REST (стандарт для синхронных сервисных вызовов).

### Почему ML Service отделён от Backend

ML Service не знает о MQTT, базе данных и устройствах. Он принимает числовой вектор — возвращает решение. Это даёт три преимущества: ML можно тестировать unit-тестами без инфраструктурных моков, модель можно заменить без изменения оркестрационного слоя, и при масштабировании ML можно вынести на отдельный сервер с GPU (не актуально для диплома, но архитектурно грамотно).

### Почему SQLite, а не PostgreSQL

Для демонстрации объём данных исчисляется тысячами записей — SQLite справляется без потерь производительности. Отсутствие отдельного контейнера упрощает Docker Compose (4 контейнера вместо 5). При необходимости миграция на PostgreSQL — замена строки подключения в SQLAlchemy.

## Feature Schema (каноническая)

Единый вектор признаков используется во всей системе — от Device Simulator (источник данных) через Backend (построение вектора) до ML Service (инференс).

| Признак | Тип | Диапазон | Источник |
|---|---|---|---|
| `hour_of_day` | int | 0–23 | Виртуальное время из Simulator или системные часы |
| `weekday` | int | 0–6 (Mon=0) | Системные часы или виртуальная дата |
| `motion_hall` | int | 0 / 1 | Device Simulator: `motion_hall` |
| `motion_living` | int | 0 / 1 | Device Simulator: `motion_living` |
| `temperature` | float | 15.0–30.0 | Device Simulator: `temperature` |
| `light_level` | float | 0.0–100.0 | Device Simulator: `light_level` |
| `tv_on` | int | 0 / 1 | Device Simulator: `tv_on` |
| `minutes_idle` | int | 0–480 | Backend: рассчитывается по последнему событию движения |

**Целевые классы:** `day`, `night`, `away`, `movie` (расширяются при подтверждении новых паттернов).

## Последствия принятых решений

**Что обеспечивает эта архитектура:**

Каждый сервис тестируется изолированно — ML Service не требует MQTT, Device Simulator не требует ML, Frontend не требует реальных устройств. Параллельная разработка — команда (или агенты) могут работать над разными сервисами одновременно, опираясь на spec-файлы как контракты. Полная демонстрация стека — фронтенд, бэкенд, ML, IoT-протокол, база данных — всё написано с нуля. Визуализация ML — кастомный React-фронтенд позволяет показать уверенность классификатора, кластеры и паттерны так, как нужно для защиты.

**Что требует дополнительных усилий:**

Фронтенд написан полностью с нуля — нет готового Lovelace-дашборда. Device Simulator имитирует поведение устройств — профиль дня нужно продумать и отладить для реалистичной демонстрации. Межсервисная коммуникация — нужно обработать сценарии таймаутов и недоступности сервисов.

**Риски:**

Объём реализации значительно больше, чем в варианте с Home Assistant. Необходимо тщательно приоритизировать: сначала минимальный рабочий пайплайн (Device Simulator → MQTT → Backend → ML Service → сцена), затем фронтенд, затем расширенные функции (Pattern Review, Simulation).
